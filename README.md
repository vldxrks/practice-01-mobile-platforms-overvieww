# Аналітичний звіт: Вибір стека для стартапу-маркетплейсу

**Дисципліна:** Програмування для мобільних платформ  
**Варіант:** 1 — Вибір стека для стартапу-маркетплейсу  
**MVP термін:** 4 місяці  
**Команда:** 2 розробники з досвідом веб-фронтенду  

---

## 1. Вступ

Стартап розробляє маркетплейс послуг і має обмежений бюджет, жорсткий дедлайн 4 місяці та команду з двох фронтенд-розробників. Завдання — обрати технологічний стек, який дозволить випустити MVP вчасно, з мінімальними витратами та з можливістю подальшого масштабування.

Розглядаються три підходи: **Flutter**, **React Native** та **нативна розробка** (iOS + Android).

---

## 2. Порівняльна таблиця за критеріями

| Критерій | Flutter | React Native | Натив (iOS + Android) |
|----------|---------|--------------|----------------------|
| **Кодова база** | Єдина (Dart) | Єдина (JavaScript/TypeScript) | Дві окремі (Swift + Kotlin) |
| **Швидкість розробки MVP** | 40–60% швидше за натив | 30–50% швидше за натив | Найповільніше (базова лінія) |
| **Вартість розробки** | 40–50% нижче за натив | 30–40% нижче за натив | Найвища |
| **Поріг входу для команди** | Середній (потрібно вивчити Dart) | **Низький** — React + JS вже знайомі | Високий (нові мови та інструменти) |
| **Доступ до платіжних SDK** | Добрий, але SDK з'являються повільніше | **Відмінний** — більшість SDK доступні першими | Найкращий (прямий доступ) |
| **Продуктивність** | Близька до нативної, 60–120 FPS | Добра, але може потребувати оптимізації | Найкраща |
| **UI/UX консистентність** | **Ідеальна** — піксель-в-піксель на всіх платформах | Залежить від платформи, потрібні доопрацювання | Платформно-нативна |
| **Hot Reload** | Стабільний, субсекундний | Доступний, іноді нестабільний | Обмежений |
| **Екосистема/спільнота** | 46% ринку крос-платформи | 35% ринку крос-платформи | Найбільша |

## 4. Аналіз ризиків за варіантами

### 4.1 React Native

| Ризик | Ймовірність | Вплив | Заходи пом'якшення |
|-------|-------------|-------|-------------------|
| UI-розбіжності між iOS та Android | Середня | Середній | Використання UI-бібліотек (React Native Paper, NativeBase), ретельне тестування |
| Продуктивність при складних анімаціях | Низька | Середній | Нова архітектура React Native (0.82+) усунула більшість проблем |
| Залежність від нативних модулів | Середня | Високий | Використання Expo або перевірених бібліотек |

### 4.2 Flutter

| Ризик | Ймовірність | Вплив | Заходи пом'якшення |
|-------|-------------|-------|-------------------|
| Вивчення Dart забирає час | Середня | Середній | Інтенсивний онбординг (2–3 тижні) |
| Менше платіжних SDK | Низька-Середня | Низький | Більшість SDK вже мають Flutter-версії |
| Розмір APK більший | Низька | Низький | Оптимізація збірки |

### 4.3 Нативна розробка

| Ризик | Ймовірність | Вплив | Заходи пом'якшення |
|-------|-------------|-------|-------------------|
| **Не вкластися в 4 місяці** | **Висока** | **Критичний** | Наймання додаткових розробників (збільшення бюджету) |
| Висока вартість ($50K–$300K+) | Висока | Високий | Пошук інвестицій |
| Подвійне тестування та підтримка | Висока | Високий | Автоматизація тестування |

## 5.Рекомендація

### 🏆 Обираємо: **React Native**

**Три аргументи на користь React Native:**

1. **Найнижчий поріг входу** — команда вже має досвід роботи з React та JavaScript/TypeScript. Це означає нульовий час на вивчення нової мови (на відміну від Dart у Flutter) та можливість почати розробку негайно.

2. **Найкращий доступ до платіжних SDK** — React Native має перевагу в екосистемі платіжних рішень (Stripe, Revolut, Paymob та інші виходять з React Native SDK першими). Для маркетплейсу послуг це критичний фактор.

3. **Швидкість виходу на ринок** — React Native дозволяє створити MVP за 3–4 місяці з економією 30–40% порівняно з нативною розробкою. Це ідеально вписується в 4-місячний дедлайн стартапу.

**Визнаний ризик:**

> React Native може потребувати додаткових зусиль для досягнення ідеальної UI-консистентності між iOS та Android через різну інтерпретацію нативних компонентів. Це може призвести до додаткових годин на доопрацювання та тестування. Однак для MVP маркетплейсу цей ризик є прийнятним, оскільки основна цінність — у функціональності, а не в ідеальному дизайні.

## 6. Умови, за яких рекомендація зміниться

| Умова | Нова рекомендація | Обґрунтування |
|-------|-------------------|---------------|
| Команда поповнюється Dart-розробником або є час на навчання (2+ тижні) | **Flutter** | Краща продуктивність, ідеальна UI-консистентність, зростаюча екосистема |
| Бюджет дозволяє найняти 2 окремих нативних команди | **Нативна розробка** | Максимальна продуктивність, найкращий доступ до API платформ |
| Застосунок потребує складної анімації або AR/VR | **Flutter або Native** | React Native може не забезпечити потрібну плавність |
| Пріоритет — швидке тестування гіпотези (2–3 місяці) | **Flutter (з FlutterFlow)** | FlutterFlow може скоротити UI-розробку на 40–60% |
